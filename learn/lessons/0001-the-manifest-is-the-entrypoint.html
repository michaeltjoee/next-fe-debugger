There is no main(): the manifest is the entrypoint

You asked where this repo starts. The answer is five places at once, and the reason why explains most of the code you'll read later.

Your win for this lesson Point at any file in src/ and say three things: who starts it, when, and what it can see.

Chrome is the program; you supply the parts

A Next.js app or a CLI has one entry file. A Chrome extension doesn't. Chrome is the running program, and it learns what your extension contains by reading manifest.json from the folder you load. “The only prerequisite is to place the manifest.json file in the extension's root directory.” Chrome Docs, Hello World Every key in that file that names a script or page is an entrypoint: Chrome starts it, at a moment Chrome chooses, in a place Chrome chooses.

One wrinkle first: the manifest points into dist/, not src/. npm run build runs tsc to turn src/**/*.ts into dist/**/*.js, then scripts/copy-static.js copies every non-.ts file (the HTML, CSS and fonts) alongside. So edit src/, build, then reload the extension.

The walls: “worlds”

The two orange boxes run in the same browser tab but can't see each other's variables. Chrome calls each one a world. “An isolated world is a private execution environment that isn't accessible to the page or other extensions.” Chrome Docs, Content scripts Both worlds share the page's DOM, but JavaScript variables like window.__NEXT_DATA__ exist only in the MAIN world, where the page's own scripts run.

Three design decisions in this repo follow directly from that wall:

  1. content.ts reads a <script> tag, not a variable. It's in the isolated world, so window.__NEXT_DATA__ is invisible to it. But Next.js also writes the same JSON into <script id="__NEXT_DATA__">, which is DOM, so it parses that instead (src/content.ts:1-2 says exactly this).
  2. gateway-hook.ts must run in the MAIN world, at document_start. Its job is to replace the page's window.fetch with a recording wrapper. Only the MAIN world has the page's fetch, and document_start runs “before any other DOM is constructed or any other script is run”, so the wrapper is in place before the page makes its first call.
  3. The popup and panel have to ask Chrome to run code in the page. They're on the blue side, with no window into the page at all. That's what the two blue arrows are, and it's the whole of Lesson 2.

Trace one feature end to end: the toolbar icon

The smallest complete feature is the icon turning blue on Next.js pages. Three hops, two files.

src/content.ts:4-14 (simplified) · isolated world, every page 
(() => {
  const el = document.getElementById("__NEXT_DATA__");   // DOM: visible from the isolated world
  let page: string | undefined;
  if (el) {
    try { page = (JSON.parse(el.textContent ?? "") as NextData).page; } catch {}
  }
  const msg: NextDataDetectedMessage = { type: "next-data-detected", found: !!el, page };
  chrome.runtime.sendMessage(msg);                        // hop across to the extension side
})();
src/background.ts:7-18 (simplified) · service worker 
chrome.runtime.onMessage.addListener((msg, sender) => {
  const tabId = sender.tab?.id;                           // which tab sent it
  if (msg?.type !== "next-data-detected" || !tabId) return;
  chrome.action.setIcon({ tabId, path: msg.found ? ICONS.active : ICONS.idle });
  chrome.action.setTitle({ tabId, title: /* … */ });
});

Why not set the icon straight from content.ts? Because content scripts may only use a short list of extension APIs: dom, i18n, storage and parts of runtime, including sendMessage. “Content scripts are unable to access other APIs directly. But they can access them indirectly by exchanging messages with other parts of your extension.” Chrome Docs chrome.action isn't on it, so the content script sends a message and the service worker, which can call chrome.action, does the work. Passing tabId makes the icon change for that tab only.

Practice: retrieve, don't re-read

Answer from memory. Scroll up only after you've committed to an answer.

A page starts loading. Which of this extension's scripts runs first?

  1. gateway-hook.js in the MAIN world
  2. content.js in the isolated world
  3. background.js in the service worker
  4. panel.js in the DevTools page

gateway-hook.js is declared with run_at: document_start, before any page script. content.js waits for document_idle; background.js only wakes for events; panel.js only exists while DevTools is open.

Why does content.ts parse the <script id="__NEXT_DATA__"> tag instead of reading window.__NEXT_DATA__?

  1. The script tag updates on every navigation
  2. Reading window variables needs the scripting permission
  3. Its isolated world can't see page variables
  4. Content scripts can't call JSON.parse on objects

The isolated world shares the DOM with the page but not its JavaScript variables. The tag is DOM, so it's readable. (And the tag doesn't update on navigation; neither does the global.)

gateway-hook.js is declared with world: "MAIN". What would break if it ran in the isolated world instead?

  1. It could no longer read the response body text
  2. It would wrap its own fetch, not the page's
  3. Chrome would refuse to inject it at document_start time
  4. The service worker would then stop receiving its messages

Each world has its own window object. Replacing window.fetch in the isolated world changes nothing the page calls, so no ms-gateway call would ever be recorded.

Who actually changes the toolbar icon to the blue ticket?

  1. content.js, by calling setIcon during page load
  2. popup.js, after reading __NEXT_DATA__ from the page
  3. gateway-hook.js, on spotting the page's __NEXT_DATA__ global
  4. background.js, after content.js sends it a message

chrome.action isn't available to content scripts, so content.js only reports; the service worker calls setIcon with the sender's tabId.

You edit src/popup/popup.ts, reload the extension, and nothing changes. Most likely cause?

  1. manifest.json points at dist/, which wasn't rebuilt
  2. Popups stay cached until you restart Chrome
  3. The service worker holds the old popup
  4. Content scripts need the page to reload

Chrome only ever loads dist/. Run npm run build (or keep npm run watch going) first.

Trace it yourself

Press AltShiftF on a page. Using only manifest.json, src/background.ts and src/popup/popup.ts, write down every hop until the API Fetch tab is showing. Then: what happens if the popup is already open when you press it?

Reveal once you've written your trace
  1. manifest.json declares the command open-gateway with suggested_key Alt+Shift+F.
  2. Chrome fires chrome.commands.onCommand in the service worker (background.ts:26) with "open-gateway".
  3. It temporarily points this tab's popup at popup.html?tab=gateway (setPopup), opens it (openPopup, Chrome 127+), and in finally points it back at plain popup.html.
  4. popup.ts:19 reads ?tab=gateway from its own URL and starts on that tab.

Already open: openPopup fails (the error is swallowed by the empty catch). But the open popup is an extension page too, and it registers its own onCommand listener (popup.ts:32-35), so it receives the same command and switches tabs itself. One keypress, two listeners.
